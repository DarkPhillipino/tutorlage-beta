# Current Project

## What we are building

We are building a react app by the name of Tutorlage which is an on-demand academic tutoring web application designed to connect parents and students with top-performing matriculants and local tutors for both in-person and online sessions. Built with a modern full-stack web architecture, it leverages geospatial matching, structured scheduling, and strict document verification to deliver safe, hyper-local academic support. The platform creates a circular academic economy by helping recent high school graduates monetize their academic success while providing families with affordable, relatable peer mentoring.

## Process

- **Dev-server preview gotcha:** the Browser pane's `preview_start({name: "dev"})` resolves `.claude/launch.json` relative to whatever directory the session considers its root — inside a git worktree, that's the worktree's own copy of the repo, not the main checkout at `C:\Users\User\Desktop\programming\code\Tutorlage-beta\tutorlage-beta`. Since real edits happen in the main checkout, a server started that way serves a stale, possibly out-of-date source tree (confirmed once via the served module's embedded sourcemap `fileName`, which pointed at the worktree path). To preview real changes, start `npm run dev` explicitly with a `cd` into the main checkout via Bash (`run_in_background: true`), then open the Browser pane at that port with `preview_start({url: "http://localhost:3000"})` instead of `{name: "dev"}`.
- `App.tsx` owns all state (booking form, user account, modals, toast) and passes it down as props — components stay presentational.
- Styling is Tailwind utility classes written inline, no separate CSS files per component. Existing palette: background `#FAF7F2`, text `#0F172A`, accent green `#15803D`.
- There is no mock data — `src/data/mockData.ts` was deleted. Institutions, tutors, tiers, and subject autocomplete all come from live Supabase queries in `src/lib/queries.ts`. The DB is currently near-empty (0 institutions, 1 seeded tutor), so components must handle loading and empty states properly, not assume rows exist. Booking a tutor still just triggers a toast — no `sessions`/`session_requests` write yet.

- **`schools_institutions` (2026-09-02): fully seeded — 26 universities + 50 TVET colleges + 25,490 K-12 schools, all real data, none fabricated.** The K-12 rows came from the DBE EMIS "Master List of Schools 2023 Q3" (CC-BY, via [DataFirst](https://www.datafirst.uct.ac.za/dataportal/index.php/catalog/985) — the user registered and downloaded it themselves, per the plan below). Only rows with `DoE_Status = 'Open'` were imported (15 pending-closure rows excluded). The source CSV had known mojibake in Afrikaans names (4 distinct corrupted codepoints, e.g. `ﾊ`→`ê`, `ﾋ`→`ë` — found by scanning every non-standard character in the file and cross-referencing context, not guessed) — fixed before import. **Import mechanism:** the ~25k rows were converted to JSON and bulk-POSTed directly to the Supabase REST API (`/rest/v1/schools_institutions`) via `curl -d @file.json` using the service-role key, in batches of 1000 — deliberately *not* relayed through chat as SQL text, which would have cost millions of tokens for no benefit. If another large dataset needs importing later, use this same pattern (Node script → JSON batches → curl bulk POST with service-role key), not inline SQL.
- **`subjects` and `grade_levels` reference tables (2026-09-02), both fully wired in.** `subjects` (59 rows, official CAPS/NSC list) and `grade_levels` (21 rows, Grade R through PhD/Adult, ordered by `sort_order`) back `fetchSubjectSuggestions()`/`fetchGradeLevelSuggestions()` in `queries.ts`, which `BookingForm.tsx`'s two autocomplete fields now call on mount — the old hardcoded `GRADE_LEVEL_OPTIONS` array is gone. Institution is still **not** filterable — `tutor_profiles` has no institution column in the schema at all.
- **Internationalization tables added (2026-09-03), schema-only — the frontend has not been touched.** `countries`, `currencies`, `languages`, `curricula`, `tutor_languages` all exist and are seeded (see `CLAUDE.md`'s routing table for row counts), and `schools_institutions.country_code`/`curriculum_id`, `tutor_profiles.currency_code`, `sessions.currency_code`, `tier_definitions.currency_code`, `payouts.currency_code`, `platform_disputes.currency_code` all exist and are backfilled to `ZA`/`ZAR` for every current row. ## Database (Supabase)

- `src/lib/supabaseClient.ts` exports `supabase`, a client built from `VITE_SUPABASE_URL` + `VITE_SUPABASE_PUBLISHABLE_KEY` (see `.env.example`). `src/lib/queries.ts` holds all the actual query functions (`fetchInstitutions`, `fetchTutors`, `fetchSubjectSuggestions`, `fetchTierDefinitions`, `fetchTutorDashboard`, `fetchTutorReviews`, `fetchTutorAvailability`, `addTutorAvailabilitySlot`, `deleteTutorAvailabilitySlot`) — components call those, they don't write raw `supabase.from(...)` calls inline.
- **Tutors can now set their own working hours (2026-09-02)**, via `AvailabilityEditor.tsx` (day-of-week + start/end time, add/remove) in the "Teaching" tab. It's the write counterpart to `TutorCalendar.tsx`'s read-only view — writes go through `addTutorAvailabilitySlot`/`deleteTutorAvailabilitySlot` in `queries.ts`, legal now because RLS's existing "Tutors manage own availability" policy (`auth.uid() = tutor_id`) was already there, just missing the base `INSERT`/`UPDATE`/`DELETE` grant (see gotcha below).
- Safe to query directly from components/hooks: every table has Row Level Security enabled, so the publishable key can only do what RLS policies allow.
- **Gotcha learned the hard way:** RLS policies alone aren't enough — Postgres also requires a base `GRANT SELECT ON <table> TO anon, authenticated` before RLS is even evaluated. Missing grants show up as HTTP 401 with `permission denied for table X` (Postgres code `42501`), which looks like an auth/key problem but isn't — check `GRANT`s first if a table that should be publicly readable 401s.
- **Same gotcha applies to `service_role`, discovered during the schools bulk import (2026-09-02).** `service_role` bypasses RLS but still needs its own base `GRANT` — it had none on `schools_institutions` (`insert`/`update`/`delete` all missing), so a service-role REST call still 403'd with the same `42501`. Don't assume `service_role` "just works" on a table you haven't explicitly granted it on.
- **Another RLS gotcha:** a table's RLS policy can reference a *different* table in its `USING` clause (e.g. `sessions`'s parent-access policy subqueries `parent_student_links`) — Postgres needs `SELECT` on that referenced table too, for *every* role touching the first table, even via an unrelated policy. Found via `parent_student_links` blocking a tutor's own `sessions` read. If a table 403s and its own grants look fine, check what its policies reference.
- **Not every table is meant to be publicly readable, and that's correct, not a bug to work around.** `sessions`, `tutor_payout_accounts`, and `tutor_verification_documents` have RLS policies scoped to `auth.uid() = tutor_id` (or `student_id`) with no public-read policy — the anon key genuinely cannot and should not read them without real auth. Don't add a public GRANT to "fix" a 401/empty-result on those; that would defeat the RLS policy's intent. `reviews` and `tutor_availability`, by contrast, do have an explicit public-read policy (`qual: true`) and only needed the base grant.

## What good work looks like

- New UI reuses the existing modal pattern (see `PricesModal.tsx`, `ScheduleModal.tsx`, etc.) and the toast pattern in `App.tsx`, rather than introducing a new UI primitive.
- Component props are typed via `src/types.ts`, not ad hoc inline types.
- New colors/spacing stay consistent with the existing palette above instead of introducing new one-off values.

## Out of scope

Express server code, calling the Gemini API, reading `.env` secrets — that's the backend workspace (`server/CONTEXT.md`). If a task needs to bypass RLS or touch a secret, that's a signal to loop in the backend workspace, not to fetch directly from a component.
